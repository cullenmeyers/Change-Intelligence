Shopify Returns API migration guide: returnProcess, returnRefund, and 2025-07

Reviewed August 31, 2026 Evidence confidence: Official Shopify developer changelog and docs Primary domain: Returns / refunds / exchanges
Current decision Treat this as a migration project, not a simple rename. Apps that create returns, approve return requests, process refunds, manage exchanges, or calculate return financial outcomes should move return completion to returnProcess, read Return.suggestedFinancialOutcome, and test refunds, exchange items, duties, shipping, and user errors together.

What changed?

Shopify's Admin GraphQL API 2025-07 officially launched return processing APIs. The key migration is from older return-refund handling to a return-processing flow:

Old surfaceNew surfaceWhy it matters
returnRefundreturnProcessReturn disposition, exchange item handling, and optional financial processing move into one return-processing step.
Return.suggestedReturnRefundReturn.suggestedFinancialOutcomeApps should calculate the recommended financial result from the newer return financial outcome model.
Return.suggestedRefundReturn.suggestedFinancialOutcomeOlder suggested-refund reads are deprecated in the migration path described by Shopify.
Refund-only return flowReturn processing flowReturns can involve restocking, disposal, exchange line items, shipping refunds, duty refunds, and financial transfers.

Who is affected?

This affects Shopify apps and integrations that use the Admin GraphQL API for return management, especially apps that:

  • Create returns with returnCreate.
  • Approve return requests with returnApproveRequest.
  • Issue return refunds through returnRefund or older refund logic.
  • Read Return.suggestedReturnRefund or Return.suggestedRefund.
  • Coordinate exchanges, restocking, disposal, refund shipping, refund duties, or return-line-item financial transfers.
  • Maintain support, returns, ERP, 3PL, accounting, or customer-service tooling around Shopify return data.

What can break?

  • Deprecated mutation risk: apps that keep building around returnRefund are building on a deprecated return-refund path.
  • Financial outcome mismatch: refund and exchange logic can drift if the app still reads old suggested-refund fields instead of suggestedFinancialOutcome.
  • Exchange handling errors: Shopify says exchange fulfillment orders are created when exchange line items are processed, so exchange behavior must be tested through the return-processing flow.
  • Partial-return complexity: refunds, duties, shipping refunds, item disposition, and exchange items need to be tested together, not as isolated refund calls.
  • Permission surprises: the return-processing mutation requires return-writing access scopes, and refunding may require the user permission to refund orders.

Return-processing flow to test

  1. Create or approve the return. Keep existing returnCreate or approval flow only where it still matches Shopify's current return lifecycle.
  2. Query the return state. Fetch the return ID, return line items, exchange line items, current status, and suggestedFinancialOutcome.
  3. Build the process input. Prepare ReturnProcessInput with the returned item quantities, exchange line item quantities, disposition decisions, notification choice, and any financial transfer details.
  4. Call returnProcess. Handle userErrors as first-class migration failures, not just logs.
  5. Verify downstream results. Check the processed return, created exchange fulfillment orders, refund transaction records, merchant financial reports, customer notifications, and any app-side sync jobs.

Minimal mutation shape

This is not a complete production payload. It is the shape your migration should be organized around:

mutation ProcessReturn($input: ReturnProcessInput!) {
  returnProcess(input: $input) {
    return {
      id
      status
    }
    userErrors {
      field
      message
      code
    }
  }
}

Smallest safe migration

  1. Inventory all return/refund surfaces. Search code, jobs, webhook consumers, support dashboards, and internal tools.
  2. Separate return-driven refunds from standalone refunds. Do not blindly replace every refund call if it is not part of a return workflow.
  3. Replace deprecated return-refund reads. Move return financial previews to Return.suggestedFinancialOutcome.
  4. Move return completion to returnProcess. Include item quantities, exchange line items, dispositions, and optional financial transfer details.
  5. Update permissions and error handling. Confirm access scopes and refund permissions, and treat userErrors as a required migration surface.
  6. Run the full matrix above in staging. Test refund, exchange, shipping, duties, restock/dispose, partial returns, and failed/error states.
  7. Ship behind a controlled release. Monitor return processing, support tickets, financial reports, webhook jobs, and fulfillment-order creation after release.
Do not over-migrate blindly. This page is specifically about Shopify return-processing flows. A refund that is not tied to a return lifecycle may need separate treatment. Confirm the business meaning of each call before replacing it.
